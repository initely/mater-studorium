## 1. Видение и цели

**Видение.** Короткие ежедневные сессии (5 минут) возвращают знания, которые иначе уходят без практики. Вопросы разных форматов, интервальные повторения, разбор по желанию и дуэли с другом.

**Цели MVP** [решено]:
1. Вы двое пользуетесь приложением 4+ недели подряд, готовясь по инфобезу.
2. Проверить три гипотезы:
   - (а) разнообразие форматов и 5-минутный лимит удерживают лучше, чем голые карточки;
   - (б) дешёвая LLM оценивает открытые ответы на русском достаточно справедливо;
   - (в) асинхронная дуэль возвращает в приложение.
3. Собрать конвейер контента, на котором официальная колода в 80 знаний собирается за ≤ 8 часов вашего времени.

**Не-цели MVP** (явно не делаем):
- генерация вопросов внутри приложения, в том числе из конспектов пользователя (v1);
- пользовательские публичные колоды и модерация пользовательского контента;
- iOS, realtime-комнаты, лиги, XP, рейтинги, чат с AI по вопросу;
- платежи, подписки, BYOK (v1);
- импорт PDF, фото и Anki в приложение;
- оценка произношения или аудио: голос используется только как диктовка текста;
- собственная админка: модерация жалоб идёт через Supabase Dashboard.

**Метрики успеха бета-версии** (через 4 недели после выдачи 10–30 пользователям):

| Метрика | Порог |
|---|---|
| Активны на 4-й неделе (хотя бы 1 сессия за неделю) | ≥ 50% бета-пользователей и оба автора |
| Медиана сессий в неделю у активных | ≥ 4 |
| Доля показанных вопросов, на которые пожаловались | < 2% |
| Согласие LLM-оценки с человеком (eval-набор, T07) | ≥ 85% по вердикту |
| Доля оценок открытых ответов с нажатым «не согласен» | < 5% |
| Затраты на LLM в рантайме | ≤ $0.5 на активного пользователя в месяц, ≤ $20 в месяц всего |
| Начатые дуэли, которые завершены обоими | ≥ 50% |

## 3. Функциональные требования

У каждого модуля есть критерии приёмки (AC). Каждый AC проверяется тестом или ручным сценарием.

### M1. Аутентификация и профиль
- При первом запуске выполняется Supabase anonymous sign-in, профиль создаётся автоматически триггером.
- В настройках анонимный аккаунт можно привязать к Google: identity linking, прогресс сохраняется.
- **AC1.1** Новый запуск без сети: приложение открывается, а вход откладывается до появления сети. Локальные данные работают.
- **AC1.2** После привязки Google на другом устройстве видны те же `user_item_state` (T21).
- **AC1.3** Пользователь A не может прочитать или записать данные пользователя B: RLS-тест на каждую таблицу.

### M2. Каталог и загрузка колод
- Каталог показывает колоды с `visibility = public`, а также свои `private` и `unlisted` колоды.
- Колода скачивается из Supabase Storage как JSON и распаковывается в локальную БД. Если `version` на сервере больше локальной, колода обновляется. Прогресс по `item_id` сохраняется, удалённые знания помечаются как `retired`.
- **AC2.1** Колоду на 500 знаний можно скачать и распаковать меньше чем за 3 секунды на среднем Android.
- **AC2.2** После обновления версии колоды прогресс по неизменённым `item_id` не сбрасывается.
- **AC2.3** Повреждённый JSON (не проходит схему) не ломает приложение: показывается ошибка, остаётся старая версия.

### M3. Сессия повторения
- Кнопка «Начать (5 мин)». Очередь строится так: сначала просроченные и сегодняшние знания по `due`, затем новые, не больше `new_per_day` (по умолчанию 10).
- Сессия заканчивается по таймеру (5 минут, начатый вопрос можно дописать) или когда очередь пуста. Затем экран итогов.
- **AC3.1** Unit-тест построителя очереди: правильный порядок, лимит новых, пустая очередь.
- **AC3.2** Сессию прервали, закрыв приложение: уже данные ответы сохранены, FSRS обновлён.
- **AC3.3** Если ничего не пора повторять, показывается пустое состояние со временем следующего повторения и кнопкой «Взять новые».

### M4. Форматы вопросов
Реестр `QuestionType → (виджет, грейдер)`. Новый формат добавляется без изменений в коде сессии.

| Тип | Фаза | Как отвечают | Проверка |
|---|---|---|---|
| `mcq` | a | один или несколько вариантов, порядок перемешан | локально, по совпадению множеств |
| `flip` | a | «Показать ответ», затем самооценка | самооценка |
| `open` | a | текст или диктовка | LLM по рубрике (M5) |
| `cloze` | b | ввод в пропуски | локально: нормализация и допустимые варианты, опечатка ≤ 1 символ при длине ≥ 6 |
| `order` | b | перетаскивание или кнопки ↑↓ | локально |
| `find_error` | b | тап по строке или строкам | локально, по совпадению множеств строк |

- **AC4.1** Каждый виджет имеет widget-тест: отрисовка из payload, ввод, правильный и неправильный ответ.
- **AC4.2** Каждый локальный грейдер имеет unit-тесты на граничные случаи (см. §4.3).
- **AC4.3** У `order` есть альтернатива перетаскиванию (кнопки ↑↓) для доступности и web.

### M5. Оценивание открытого ответа
См. §4.2. Edge Function `grade-open-answer`.
- **AC5.1** Ответ приходит меньше чем за 6 секунд для 95% запросов. Таймаут 15 секунд, после него фолбэк на самооценку.
- **AC5.2** Без сети, при исчерпанном лимите или ошибке модели пользователь видит эталонный ответ и оценивает себя сам. Ответ не теряется.
- **AC5.3** Одинаковый нормализованный ответ на тот же вопрос второй раз приходит из кэша (`cached: true`) без вызова модели.

### M6. Разбор по желанию
- После любого ответа сразу показывается вердикт и панель оценки. Ниже две свёрнутые кнопки: «Коротко» (`explanation_short`) и «Подробнее» (`explanation_long` в markdown плюс список источников со ссылками).
- Все тексты разборов **заранее** лежат в колоде. В рантайме LLM разборы не генерирует.
- **AC6.1** Разбор можно не открывать: «Дальше» доступна сразу.
- **AC6.2** Ссылки открываются во внешнем браузере. Каждая ссылка — из `sources` колоды.

### M7. Интервальные повторения (FSRS)
См. §4.1.
- **AC7.1** Unit-тесты: после оценки `Again` новый `due` раньше, чем после `Good`. Состояние детерминированно для фиксированного `now`.
- **AC7.2** Повторяется **знание**, а формулировка выбирается из его вариантов (правило в §4.1).

### M8. Офлайн и синхронизация
См. §7.3.
- **AC8.1** 20 ответов в авиарежиме, затем включение сети: все `review_logs` на сервере, дублей нет.
- **AC8.2** Два устройства, разные ответы по одному знанию: на сервере остаётся состояние с более поздним `updated_at`.

### M9. Напоминания
- Локальное уведомление на Android в выбранное время. Если к этому времени ничего не пора повторять, уведомление на этот день не ставится. Расписание пересчитывается после каждой сессии и при запуске приложения.
- Web: в MVP напоминаний нет [решено].
- **AC9.1** Ручной сценарий: выставили время на +2 минуты при наличии due-знаний, уведомление пришло, тап открывает экран сессии.

### M10. Асинхронная дуэль
- Создатель выбирает колоду. Клиент берёт 5 случайных вопросов **автопроверяемых** типов (`mcq`, в MVP-b также `cloze`, `order`, `find_error`) и создаёт `duel` с 6-символьным кодом.
- Создатель проходит дуэль, после чего код можно отправить другу через системный share. Соперник вводит код, при необходимости скачивает колоду и проходит те же 5 вопросов.
- Итог: количество верных ответов, при равенстве побеждает меньшее суммарное время. Экран сравнения показывает по каждому вопросу оба ответа, правильный ответ и `explanation_short`.
- Срок жизни дуэли 72 часа. Ответы в дуэли **не** влияют на FSRS [решено, пересмотреть в v1].
- **AC10.1** Чужой незавершённый ответ не виден до того, как ответил сам (RLS-тест).
- **AC10.2** Просроченный или неверный код даёт понятную ошибку.
- **AC10.3** (Should) Создатель получает push, когда соперник закончил.

### M11. Жалобы и «не согласен»
- На экране результата есть кнопка «⚑». Причины: неверный ответ, непонятно, опечатка, плохой источник, другое; можно добавить комментарий. Запись в `reports`.
- После LLM-оценки есть кнопка «Не согласен». Пользователь сам ставит оценку (`grade_source = override`), и автоматически создаётся `report` с причиной `grading_disagree`.
- **AC11.1** Жалоба отправляется офлайн через outbox.
- **AC11.2** Куратор видит жалобы в Supabase Dashboard через view `reports_inbox`: колода, вопрос, текст вопроса, причина, количество.

### M12. Конвейер контента (вне приложения)
См. §5.4. Инструменты в `tools/` и инструкция в `content/PIPELINE.md`.
- **AC12.1** `dart run tools/validate_deck.dart content/decks/x.json --release` падает, если есть знание без `review.status = approved`, ссылка на несуществующий `source_id` или вопрос без нужного для его типа payload.
- **AC12.2** `tools/check_links.dart` для каждой `ref` проверяет, что URL отвечает 200 и `quote` встречается на странице после нормализации. Для недоступных страниц (paywall и т.п.) есть явный флаг `quote_unverifiable`.
- **AC12.3** `tools/import_deck.dart` загружает колоду в Storage и upsert-ит строку в `decks` с увеличенной версией. Ключ service role берётся только из локального `.env`.

## 4. Механика повторений и оценивания

### 4.1. Алгоритм: FSRS [решено]
- Используем Dart-пакет `fsrs` из open-spaced-repetition [проверить актуальность и API]. Параметры по умолчанию, `desired_retention = 0.9`. Персональная оптимизация параметров в v1, когда наберётся ≥ 1000 логов на пользователя.
- **Единица планирования — знание (`item`)**, а не вопрос. У знания 1–4 вопроса-варианта разных типов.
- **Выбор варианта при показе:** вариант, который давно не показывался, причём тип отличается от прошлого показа этого знания. Если вариант один, берём его.
  - Новое знание при первом показе: `flip`, если есть, иначе `mcq`, иначе любой.
  - Пока стабильность знания `S < 3 дня`, `open` не показываем: сначала узнавание, потом вспоминание.
- **Шкала оценки:** Again(1), Hard(2), Good(3), Easy(4). После ответа показывается панель из 4 кнопок, предложенная оценка подсвечена. «Дальше» принимает подсвеченную, тап по другой кнопке переопределяет её.

| Источник | Предлагаемая оценка |
|---|---|
| Автопроверка: верно | Good |
| Автопроверка: неверно | Again |
| `order`: одна перестановка соседних шагов | Hard |
| `cloze`: принят с опечаткой | Hard |
| `open`: correct / partial / incorrect | Good / Hard / Again |
| `open`: unsure, ошибка, офлайн | без подсказки, оценивает сам пользователь |
| `flip` | без подсказки |

### 4.2. Оценивание открытого и голосового ответа
Голосовой ответ — это открытый ответ, введённый диктовкой. Текст распознаётся на устройстве, его можно отредактировать до отправки, `input_mode = voice` передаётся модели.

**Рубрика в колоде** (у каждого `open`-вопроса):
- `reference_answer` — эталон в 1–3 предложения;
- `rubric[]` — 2–5 ключевых пунктов `{id, text, weight (1–3), required (bool)}`.

**Конвейер проверки (Edge Function):**
1. Если ответ пустой или короче 3 символов, вердикт `incorrect` без вызова модели.
2. Нормализуем ответ: lower, trim, `ё` → `е`, схлопываем пробелы. Ищем в `grading_cache` по ключу `sha256(question_id|deck_version|normalized)`.
3. Проверяем лимит пользователя (по умолчанию 30 оценок в день) и глобальный дневной бюджет. Если превышен, возвращаем 429, клиент переходит на самооценку.
4. Вызываем модель со строгой JSON-схемой (§5.2). Невалидный JSON: один повтор, потом `unsure`.
5. **Балл считает сервер, не модель:**
   - `hit = 1`, `partial = 0.5`, `miss = 0`, взвешенное среднее по `weight`;
   - `required` пункт со статусом `miss` ограничивает вердикт значением не выше `partial`;
   - `contradiction = true` (в ответе есть утверждение, противоречащее эталону) даёт `incorrect`.
6. Пороги: `score ≥ 0.8` → `correct`; `0.5 ≤ score < 0.8` → `partial`; `< 0.5` → `incorrect`. Если модель вернула `unsure`, сервер передаёт `unsure`.
7. Клиент показывает вердикт, отмеченные пункты рубрики (✓, ½, ✗), `feedback` модели (1–2 предложения, только про упущенные пункты рубрики) и эталонный ответ.

**При сомнении** (`unsure`, ошибка, таймаут): показываем эталон и рубрику, пользователь сам ставит оценку, в лог пишется `grade_source = self`. Оценку LLM всегда можно переопределить кнопкой «Не согласен» (M11).

Пороги 0.8 и 0.5 — **[предположение]**, их калибруем на eval-наборе в T07.

### 4.3. Локальные грейдеры (MVP-b)
- `cloze`:
  - нормализация как в п. 2 выше плюс удаление пунктуации по краям;
  - сравнение с `accepted[]`;
  - расстояние Левенштейна ≤ 1 при длине ≥ 6 засчитывается с пометкой «опечатка»;
  - числа сравниваются как числа;
  - несколько пропусков: верно только если верны все, в UI подсвечивается каждый пропуск.
- `order`: эталонный порядок совпадает с порядком в JSON, клиент перемешивает (без совпадения с эталоном). Полное совпадение даёт Good, одна перестановка соседних — Hard, иначе Again.
- `find_error`: `error_lines` — множество (1–2 строки). Совпадение множеств даёт верно. После ответа показываются `line_explanations`.

### 4.4. Разбор по желанию
Три уровня, все написаны заранее и вычитаны:
1. **Вердикт.** Показывается всегда, отдельной кнопки нет.
2. **«Коротко»** — `explanation_short`, 2–3 предложения. Вопрос может переопределить разбор своего знания.
3. **«Подробнее»** — `explanation_long`, markdown до ~300 слов, плюс источники: заголовок, URL, цитата.

LLM-разборы под конкретную ошибку пользователя — в v1, и только для `open` (feedback уже есть в M5).

## 5. LLM-слой

### 5.1. Задачи и классы моделей

| Задача | Когда | Где выполняется | Класс модели | Почему |
|---|---|---|---|---|
| Генерация знаний и вопросов из источников | Офлайн, куратор | Claude Code по подписке | Сильная (Opus-класс) | Качество важнее всего, в рантайме $0 |
| Верификация вопросов по источнику | Офлайн | Claude Code, **новая сессия** | Сильная или средняя | Свежий контекст не «защищает» свои же ответы |
| Разборы и подбор ссылок | Офлайн | Claude Code с web search | Сильная | Ссылки проверяются скриптом и человеком |
| Оценка открытого ответа | Рантайм | Edge Function → OpenRouter | Дешёвая (Flash, Haiku, mini-класс) [проверить цены] | Узкая задача по рубрике, объём большой |
| Перепроверка по «не согласен» | v1 | Edge Function | Средняя | Редко, нужна точность |
| Генерация из конспекта пользователя | v1 | Edge Function | Средняя | Стоимость, нужен UX правки |

**Подписка Claude.** Её используем только как инструмент куратора в Claude Code. Рантайм приложения на подписке не работает: подписка не является API-доступом [проверить условия использования]. В рантайме работают OpenRouter по общему ключу на сервере и в v1 BYOK.

### 5.2. Промпт-контракт: `grade-open-answer`

Клиент отправляет в Edge Function:
```json
{ "deck_id": "infosec-basics", "deck_version": 3,
  "question_id": "infosec.xss.reflected.q3",
  "answer_text": "...", "input_mode": "voice" }
```
Рубрику и эталон сервер берёт из своей копии колоды, а не от клиента.

Вход модели: system плюс user с JSON.

System (сжато):
> Ты экзаменатор. Оцени ответ студента **только** по пунктам рубрики и эталону. Не добавляй фактов вне рубрики. Игнорируй орфографию и ошибки распознавания речи (input_mode=voice). Синонимы и перефразирование засчитываются. Если ответ содержит утверждение, противоречащее эталону, ставь contradiction=true. Если не можешь уверенно решить, ставь verdict="unsure". Ответь строго JSON по схеме.

User:
```json
{ "question": "...", "reference_answer": "...",
  "rubric": [{"id":"p1","text":"...","required":true}],
  "student_answer": "...", "input_mode": "voice", "lang": "ru" }
```

Ответ модели (JSON Schema через `response_format`, поддержку у выбранной модели [проверить] на OpenRouter):
```json
{ "points": [{"id":"p1","status":"hit|partial|miss","evidence":"фрагмент ответа"}],
  "contradiction": false,
  "verdict": "correct|partial|incorrect|unsure",
  "feedback": "1–2 предложения про упущенное" }
```

Ответ клиенту:
```json
{ "verdict":"partial", "score":0.67,
  "points":[{"id":"p1","status":"hit"}],
  "feedback":"...", "suggested_rating":2,
  "cached":false, "remaining_quota":27 }
```

### 5.3. Защита от галлюцинаций
1. **В рантайме модель не сообщает фактов.** Она только сопоставляет ответ с рубрикой. Её `feedback` ограничен упущенными пунктами рубрики.
2. **Весь показываемый контент вычитан человеком:** вопросы, ответы, разборы, ссылки. В релиз попадают только знания с `review.status = approved` (валидатор в режиме `--release`).
3. **Каждый факт привязан к источнику:** `refs[] = {source_id, url, quote}`. Цитата должна дословно (после нормализации) находиться на странице, это проверяет `check_links`. Ссылки, которых нет в `sources`, валидатор не пропускает.
4. **Второй проход проверки:** отдельная сессия получает вопрос, ответ и цитату и отвечает, подтверждает ли цитата ответ, нет ли второго верного варианта в `mcq` и однозначна ли формулировка. Помеченные знания вычитываются особенно внимательно.
5. **Обратная связь:** жалобы и «не согласен». Знание с ≥ 2 жалобами автоматически скрывается из показа до проверки (`status = flagged` в view, клиент получает список скрытых при синхронизации).
6. **Источники только открытые:** OWASP, NIST, RFC, Википедия, документация вендоров. Учебники вроде Cambridge используются только в личных колодах (`private`), в каталог не попадают из-за авторских прав. Для CC BY-SA источников указываем атрибуцию.

### 5.4. Конвейер контента (Claude Code, куратор)
```
источники (URL, свои заметки) → [1] генерация JSON знаний (сессия A)
  → [2] validate_deck (схема) → [3] check_links (URL + цитаты)
  → [4] верификация (сессия B, новая) → [5] вычитка человеком: review.status=approved
  → [6] validate_deck --release → [7] import_deck → Supabase
```
Промпты шагов 1 и 4 лежат в `content/prompts/`. Генерация идёт порциями по 10–15 знаний на одну подтему.

### 5.5. Кэш, лимиты, стоимость
- Кэш оценок: `grading_cache`, TTL не ограничен. Ключ включает `deck_version`, поэтому после правки вопроса кэш автоматически перестаёт совпадать.
- Лимиты: 30 оценок в день на пользователя и глобальный дневной лимит `$1` (env). При превышении 429, клиент переходит на самооценку.
- `llm_usage` пишет каждую оценку: токены, модель, стоимость, попадание в кэш.

**Оценка стоимости [проверить цены на openrouter.ai]:**

| Параметр | Значение |
|---|---|
| Токенов на вызов | ~700 вход + ~250 выход |
| Цена дешёвого класса | ~$0.1–0.4 за 1M входа, ~$0.4–1.6 за 1M выхода |
| Стоимость вызова | ≈ $0.0002–0.0007 |
| Вызовов на активного пользователя в месяц | 20 в день × 30 = 600 (верхняя граница, кэш срежет) |
| Итого на пользователя | ≈ $0.12–0.42 в месяц, укладывается в $0.5 |
| 30 пользователей | ≤ ~$13 в месяц |

### 6.2. Бэкенд: сравнение и выбор

| Критерий | **Supabase** | Firebase | Свой сервер (Docker: Postgres + API) |
|---|---|---|---|
| Модель данных | Postgres, SQL, RLS | Firestore (документы), сложные запросы неудобны | Любая |
| Аутентификация | Anonymous, Google, identity linking [проверить] | Anonymous, Google, linking | Писать самому |
| Серверная логика | Edge Functions (Deno/TS) | Cloud Functions (нужен Blaze-план с картой [проверить]) | Своя |
| Realtime для v1 | Broadcast/Presence | RTDB/Firestore listeners | Писать самому |
| Push | Нет, нужен FCM | FCM нативно | FCM |
| Стоимость беты | Free tier; проект засыпает после ~7 дней неактивности [проверить] | Spark бесплатно, но функции требуют Blaze | VPS ~$5 в месяц + администрирование |
| Выход из вендора | Self-host на Docker, ты умеешь | Сложно | — |
| Под твой опыт (SQL, Docker) | ✔ | Нужно учить NoSQL | ✔, но времени нет |

**Выбор: Supabase** [решено]. SQL и RLS тебе знакомы и хорошо проверяются тестами. Edge Functions прячут ключ OpenRouter. Есть путь к self-host. Firebase подключаем **только ради FCM** (push), без Firestore и Functions.

### 6.3. Серверные компоненты
- **Postgres**: таблицы из §7.2, RLS на всех таблицах, миграции в `supabase/migrations/`.
- **Storage**: bucket `decks/` с JSON колод. Публичное чтение для `public`, для остальных — подписанные URL.
- **Edge Functions**:
  - `grade-open-answer`: M5;
  - `notify-duel`: вызывается Database Webhook на завершение дуэли [проверить], шлёт FCM HTTP v1;
  - `delete-account`: v1, обязательно для Google Play.
- **SQL RPC**:
  - `upsert_item_states(jsonb)` — LWW;
  - `join_duel(code)`;
  - `hidden_questions()` — знания с ≥ 2 жалобами.

### 6.4. Realtime
В MVP не нужен: дуэль асинхронная, состояние читается при открытии экрана и по push. В v1 realtime-комната строится на Supabase Realtime Broadcast и Presence.

### 6.5. Push
FCM (Android и web; на web нужен `firebase-messaging-sw.js`). Таблица `devices` хранит токены. Напоминания на Android — локальные уведомления, без сервера.

- Android: подписанный APK в GitHub Releases. Google Play ($25, обязательное удаление аккаунта) — в v1.

## 7. Модель данных

### 7.1. Колода (JSON, источник истины для контента) [решено, ADR-7]
Контент хранится как версионированный JSON со стабильными строковыми ID. В MVP контент в нормализованные таблицы Postgres **не** раскладываем: сервер хранит метаданные колоды и файл.

```json
{
  "schema_version": 1,
  "id": "infosec-basics", "version": 3, "lang": "ru", "topic": "infosec",
  "title": "Основы ИБ", "description": "...",
  "sources": [{"id":"owasp-xss","title":"OWASP: XSS","url":"https://...","license":"CC BY-SA 4.0"}],
  "items": [{
    "id": "infosec.xss.reflected",
    "title": "Reflected XSS", "tags": ["web","xss"],
    "fact": "Краткая формулировка знания",
    "explanation_short": "...", "explanation_long": "markdown...",
    "refs": [{"source_id":"owasp-xss","quote":"...","quote_unverifiable":false}],
    "review": {"status":"approved","by":"tel","notes":""},
    "questions": [
      {"id":"infosec.xss.reflected.q1","type":"mcq","prompt":"...",
       "payload":{"options":[{"id":"a","text":"..."},{"id":"b","text":"..."}],"correct":["b"],"multiple":false}},
      {"id":"...q2","type":"flip","prompt":"...","payload":{"back":"..."}},
      {"id":"...q3","type":"open","prompt":"...",
       "payload":{"reference_answer":"...","rubric":[{"id":"p1","text":"...","weight":2,"required":true}]}},
      {"id":"...q4","type":"cloze","prompt":"XSS расшифровывается как {{1}}",
       "payload":{"blanks":[{"id":"1","accepted":["cross-site scripting","межсайтовый скриптинг"]}]}},
      {"id":"...q5","type":"order","prompt":"...","payload":{"steps":[{"id":"s1","text":"..."}]}},
      {"id":"...q6","type":"find_error","prompt":"...",
       "payload":{"mode":"code","language":"nginx","lines":["..."],"error_lines":[3],"line_explanations":{"3":"..."}}}
    ]
  }]
}
```
Правила:
- ID стабильны между версиями.
- Изменение смысла вопроса означает новый ID.
- Удаление знания из колоды означает `retired` на клиенте, прогресс не удаляется.

### 7.2. Сервер (Postgres)

| Таблица | Ключевые поля | RLS |
|---|---|---|
| `profiles` | `id` (= auth.uid), `display_name`, `timezone`, `created_at` | свой профиль; `display_name` видно соперникам в дуэли |
| `decks` | `id` (text), `title`, `topic`, `lang`, `version`, `owner_id?`, `visibility` (public/unlisted/private), `storage_path`, `item_count`, `updated_at` | чтение: public, unlisted (по id), свои; запись: только service role |
| `user_item_state` | PK(`user_id`, `item_id`), `deck_id`, `due`, `stability`, `difficulty`, `elapsed_days`, `scheduled_days`, `reps`, `lapses`, `state`, `last_review`, `last_question_id`, `updated_at` | только свои |
| `review_logs` | `id` uuid (от клиента), `user_id`, `deck_id`, `deck_version`, `item_id`, `question_id`, `question_type`, `rating`, `grade_source` (self/auto/llm/override), `llm_score?`, `answer_text?`, `duration_ms`, `reviewed_at` | только свои, insert-only |
| `reports` | `id`, `user_id`, `deck_id`, `deck_version`, `question_id`, `reason`, `comment`, `status` (new/accepted/rejected/fixed), `created_at` | insert свои; чтение: service role |
| `grading_cache` | `key` (sha256), `result` jsonb, `model`, `created_at` | только service role |
| `llm_usage` | `id`, `user_id`, `task`, `model`, `tokens_in`, `tokens_out`, `cost_usd`, `cached`, `created_at` | только service role |
| `duels` | `id`, `code` (unique), `deck_id`, `deck_version`, `question_ids` text[], `creator_id`, `opponent_id?`, `status` (open/active/finished/expired), `created_at`, `expires_at` | участники; поиск по коду только через RPC `join_duel` |
| `duel_answers` | PK(`duel_id`, `user_id`, `question_id`), `answer` jsonb, `is_correct`, `duration_ms`, `answered_at` | свои всегда; чужие только после того, как сам ответил на все 5 |
| `devices` | `id`, `user_id`, `fcm_token` (unique), `platform`, `updated_at` | только свои |

Плюс view `reports_inbox` для куратора: агрегат по `question_id`.

### 7.3. Локально (drift) и синхронизация

| Локальная таблица | Источник | Направление синхронизации |
|---|---|---|
| `decks`, `items`, `questions` | JSON колоды | только pull (скачивание колоды) |
| `user_item_state` + `dirty` | клиент | push (LWW) и pull при запуске |
| `review_logs` + `synced_at` | клиент | push (идемпотентно по `id`) |
| `outbox` (reports, duel_answers) | клиент | push |
| `hidden_questions` | сервер | pull |

**Алгоритм:** offline-first. Каждый ответ сначала пишется локально, в одной транзакции: `review_log`, новое `user_item_state` с `dirty = 1`. `SyncService` запускается при старте, после сессии и при появлении сети:
1. Push `review_logs`, у которых `synced_at` пуст: upsert с `on conflict (id) do nothing`.
2. Push dirty `user_item_state` через RPC `upsert_item_states`. Сервер применяет запись, только если `updated_at` новее.
3. Push `outbox`.
4. Pull `user_item_state` с `updated_at > last_pull_at` и LWW-слияние.
5. Pull `hidden_questions` и метаданных колод (версии).

Конфликт по одному знанию с двух устройств решает LWW. Этого достаточно для беты. Пересмотр — в ADR-14.

## 8. UX

### 8.1. Карта экранов
```
Онбординг (1 экран: выбрать колоду + время напоминания)
 └─ Главный
     ├─ [Начать 5 мин] → Сессия → Итоги сессии → Главный
     ├─ Колоды → Колода (прогресс: новые / изучаемые / выученные) → [Начать по этой колоде]
     ├─ Дуэли → Создать (выбор колоды → играть → поделиться кодом)
     │        → Ввести код → играть → Результат дуэли (сравнение)
     └─ Настройки (привязать Google, время напоминаний, новых в день, о приложении / приватность)
Шторка «Пожаловаться» — из экрана результата вопроса
```

### 8.2. Главный сценарий: «сессия на 5 минут»
1. Пуш «Есть что повторить» (или запуск приложения). Главный экран: «12 к повторению, 5 новых», большая кнопка «Начать · 5 мин», ниже карточки ожидающих дуэлей.
2. Сессия: тонкий прогресс-бар времени сверху, в центре вопрос, внизу контрол ответа своего формата.
3. После ответа вердикт (цвет и иконка, не только цвет), под ним панель оценки (4 кнопки, предложенная подсвечена), ниже свёрнутые «Коротко», «Подробнее» и иконка ⚑.
4. «Дальше» (или тап по оценке) открывает следующий вопрос. Переход меньше 100 мс, вопросы заранее загружены из drift.
5. Время вышло: текущий вопрос можно доответить, затем итоги («повторено 14, верно 11, следующее повторение через 3 ч») и кнопка «Ещё 5 минут».

### 8.3. Открытый ответ и голос
- Поле ввода с кнопкой 🎤. Удержание или тап начинает диктовку, текст распознаётся в реальном времени прямо в поле, его можно править до отправки.
- Нет разрешения на микрофон: однократное объяснение. При отказе кнопка скрыта, текстовый ввод работает.
- Во время проверки скелетон «Проверяю…» (до 15 секунд), затем вердикт, пункты рубрики (✓, ½, ✗), feedback и эталон, кнопка «Не согласен».

### 8.4. Дуэль
- Создание: колода → «Играть» (5 вопросов, у каждого таймер от 0, без лимита) → экран «Отправь код другу: `K7Q2MX`» и кнопка «Поделиться».
- Карточка дуэли на главном: «Ждём Сашу · осталось 2 д» или «Саша ответил — посмотри результат».
- Результат: счёт, время, по каждому вопросу «твой ответ / его ответ / верный» и `explanation_short`.

### 8.5. Пустые состояния и ошибки

| Ситуация | Что видит пользователь |
|---|---|
| Нечего повторять | «Всё повторено 🎉 Следующее — через 3 ч» + «Взять 5 новых» |
| Колода не скачана, нет сети | «Нужна сеть, чтобы скачать колоду» + «Повторить» |
| Открытый ответ офлайн или исчерпан лимит | «Проверка недоступна — сравни с эталоном» + самооценка |
| Ошибка или таймаут LLM | То же, без технических деталей |
| Неверный или просроченный код дуэли | «Код не найден или дуэль истекла» |
| Вопрос скрыт по жалобам | Просто не показывается |
| Ошибка синхронизации | Тихий повтор. Если ошибка держится больше 24 ч, маленький значок на настройках |

## 9. Нефункциональные требования

| Область | Требование |
|---|---|
| Производительность | Холодный старт ≤ 2,5 с на среднем Android (2021+); переход между вопросами ≤ 100 мс; распаковка колоды на 500 знаний ≤ 3 с |
| Офлайн | Сессии по скачанным колодам полностью офлайн, кроме проверки `open` (фолбэк). Ни один ответ не теряется |
| Приватность | Регистрация не нужна. PII не требуется. Текст открытых ответов уходит в OpenRouter и провайдера модели, пользователь предупреждён один раз перед первым `open`. Аудио не покидает устройство. Ключи OpenRouter и service role не попадают в клиент. Регион Supabase — ближайший к пользователям [предположение: EU] |
| Безопасность | RLS на всех таблицах с тестами. Edge Functions проверяют JWT. Rate limit на LLM. Секреты в `.env` и Supabase secrets |
| Доступность | Масштаб текста до 200% без обрезаний на экране сессии; Semantics-метки на контролах; цель тапа ≥ 48 dp; вердикт передаётся не только цветом; у `order` есть кнопки ↑↓ |
| Локализация | Все строки UI в ARB (`gen-l10n`) с первого дня; язык UI — ru, en в v1. Язык контента задаётся полем `lang` колоды |
| Наблюдаемость | Логи Edge Functions; `llm_usage`; Crashlytics или Sentry — в v1 |
| Качество кода | `flutter analyze` без предупреждений, `dart format`, тесты на domain и грейдеры, CI зелёный перед мержем |

## 15. Предположения
1. Репозиторий будет на GitHub (CI — Actions, web — Pages, APK — Releases).
2. Пороги оценки 0.8 и 0.5 подходят. Калибруются в T07.
3. 30 оценок `open` в день на пользователя хватает и не раздражает.
4. Регион Supabase — EU.
5. У беты ≤ 30 пользователей, free tier Supabase и FCM их выдерживает.
6. Знание с 3–4 вариантами вопросов реально собрать за ~5 минут вычитки на знание: 80 знаний ≈ 7 часов.
7. Пакеты `fsrs`, `drift` (web), `speech_to_text` (web), `flutter_markdown_plus` сейчас рабочие.
8. Друзья в бете на Android или пользуются web.
9. 5 вопросов в дуэли — правильный размер.
10. Ответы в дуэли не влияют на FSRS, и это не раздражает.

## 16. Три самых рискованных места ТЗ
1. **Оценка открытых ответов дешёвой моделью (§4.2, §5.2).** Здесь я наименее уверен в цифрах: пороги, согласие ≥ 85%, стоимость. Если T07 покажет < 80%, `open` станет «самооценкой с подсказкой LLM», а ценность формата упадёт. Поэтому T07 стоит в первой неделе.
2. **Трудоёмкость контента (§5.4, R2).** Весь продукт держится на качестве официальной колоды, а вычитка — ручной труд двух людей. Оценка «80 знаний за ~8 часов» — предположение. Если выйдет втрое дольше, колода MVP будет 30–40 знаний, и придётся решать, что важнее: широта или проверенность.
3. **Web-часть (drift wasm, Web Speech, FCM на web).** На web сходятся три технологии, у каждой есть подводные камни. Если spike T05 или push на web затянутся, честнее сделать web «только сессии без голоса и push», а не тратить на него недели.
