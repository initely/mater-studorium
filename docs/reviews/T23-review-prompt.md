# Промпт для Opus-ревью безопасности T23 (дуэль: игра и сравнение)

Запускается агентом с `model: opus`, `effort: high` (в облачной сессии: инструмент Agent, ветка `t23-duel-play`, работа в изолированном worktree или в отдельной ветке; код ревьюера НЕ меняет). Результаты ревью передаются исполнителю T23 (Sonnet) для исправлений, затем слияние в `main`.

Ты ревьюер безопасности и корректности (Postgres RLS, SECURITY DEFINER RPC, гонки, утечка данных между участниками дуэли). Проверь результат задачи T23 проекта Mater Studorium (игра в дуэль и экран сравнения). Код в ветке `t23-duel-play` (коммит 5078f15, стоит поверх `main` на 80ca837). Смотри `git diff main...t23-duel-play`. Ты единственный, кто использует локальный Supabase (docker, project_id mater_studorium): после работы обязательно `supabase stop`. НЕ скрывай вывод `supabase start`, не используй `pkill -f` с шаблоном из собственной команды.

ФАЙЛЫ НЕ РЕДАКТИРУЙ и не коммить: только читай, запускай проверки и отчитывайся. Временные эксперименты с БД допустимы, потом `supabase db reset` / `supabase stop`, `git status` чистый. `dart`, `flutter`, `deno`, `supabase` должны быть в PATH (в облаке их ставит tools/cloud/setup.sh; локально Dart берётся из Flutter SDK).

Контекст: CLAUDE.md (правила №4–№6), docs/tasks/01-mvp-a.md (карточки T22–T24), docs/TZ.md: M10, AC10.x (AC10.1: ответы до завершения не видны сопернику), §6.3, §6.4, §8.4, ADR-16 (дуэль не влияет на FSRS), ADR-30, ADR-35 (дуэль: схема, коды, доверие к клиенту; п. 6 порядок блокировок, п. 7 видимость ответов, п. 12 обязанности T23), ADR-36 (решения T23) (§14); прошлые ревью T20/T21/T22 (паттерны: default privileges, стражи 0000_guards по oid, definer vs invoker, search_path='', lock_timeout, границы timestamptz, «ядовитые» строки, оракулы существования, гонки/deadlock, мутации тестов, невидимые символы).

Предмет: supabase/migrations/0008_duel_play.sql (RPC записи ответа), supabase/tests/0009_duel_play.test.sql и 0000_guards, tools/duel_join_race.sh (сценарий 4), lib/features/duel (DuelPlayController, экран прохождения, результат, карточки главного, домен), outbox kind=duel_answer (DriftDuelAnswerQueue, duelAnswerOutboxHandler), lib/core/sync, test/integration/duel_live_test.dart, README «Дуэль: игра и результат».

Что просил проверить исполнитель:

1. 0008_duel_play.sql: порядок advisory `duels:<uid>` → строка дуэли FOR NO KEY UPDATE; условие участия в WHERE (строка чужой дуэли не блокируется); `duplicate` возвращается ДО проверки срока (чтобы запись из outbox уходила и после конца дуэли); единообразный MS404 для «нет дуэли» и «не участник» (оракул существования дуэли?). Проверь: можно ли узнать uuid чужих дуэлей; поведение при дуэли в статусе open без соперника (ответы создателя до входа соперника), expired, finished; повтор после finished; ответ на вопрос вне набора (22023); идемпотентность по ключу (дуэль, пользователь, вопрос) вместо uuid ответа: подмена `p_is_correct` повторным вызовом невозможна? (первый ответ остаётся); NULL/пустые/гигантские аргументы; p_answer jsonb размер/глубина (кап 512 байт по CHECK в 0007 считается по серверному виду jsonb, клиент считает пробелы после `:` и `,`: проверь, нет ли расхождения, из-за которого валидные ответы отвергаются и «ядовитая» запись застревает или теряется), `p_duration_ms` границы 0..сутки, отрицательные, переполнение.

2. Видимость ответов (AC10.1). Исполнитель сознательно оставил остаточный риск: политика `duel_answers_select` из 0007 отдаёт чужие ответы любому участнику, который сам уже закончил (`*_done_at`), даже пока соперник НЕ закончил и дуэль не `finished`; клиент их не запрашивает, но через API они доступны. Оцени это против ТЗ AC10.1 («ответы до завершения не видны сопернику») и ADR-35 п. 7: нарушает ли ТЗ? Предложи конкретный фикс: либо политика «чужие ответы только при status = finished» (проверь, что это не ломает чтение результата и тесты), либо отдельная RPC результата. Проверь, нельзя ли получить чужие ответы раньше (гонка done_at; подделка done_at невозможна по триггеру?), через get_duel, my_duels, realtime-подписку на duel_answers (publication supabase_realtime: включена ли таблица?), через PostgREST embed/join, через представления, через ответы собственной дуэли у создателя до входа соперника.

3. Доверие к клиенту (ADR-35 п. 2): is_correct и duration_ms приходят от клиента; для беты принято. Оцени, можно ли через это навредить другому игроку (не только накрутка счёта себе): записать ответы «за» соперника (проверка auth.uid() в RPC и триггере), заставить дуэль завершиться досрочно, «skipped: true» как способ завершить дуэль без вопросов (мгновенный finished, победа по скорости?), и что именно считается победителем (тайбрейк по времени можно накрутить duration_ms=0).

4. Клиент: DuelPlayController не знает про FSRS (ADR-16): подтверди чтением кода и тестами, что review_logs/user_item_state/outbox sync не затрагиваются; повторный ответ невозможен на трёх уровнях (проверь каждый мутацией); «Сыграть без них» отправляет `{"skipped":true}` как неверно/время 0: корректно ли для обоих игроков (оба должны получить одинаковый набор); обработка вопросов не mcq / нет в колоде / скрытых / retired; опрос статуса раз в 30 с (таймер отменяется, нет утечек, нет шторма запросов при многих дуэлях); `duel.results_seen` в app_settings (карточка «результат» 3 суток); имя соперника в изоляции U+2068…U+2069; ошибки без деталей; перенос данных при смене анонимного пользователя (shouldAdoptLocalData / outbox kind=duel_answer: ответы дуэли чужого пользователя не уходят под новым user_id; ADR-30/34).

5. outbox: handler duel_answer: «ядовитые» записи (MS404/MS410/22023/23514 отбрасываются, сеть/доступ/лимит ждут), не блокирует остальной синк, идемпотентность повторной отправки, порядок отправки, поведение при смене пользователя посреди очереди, размер ответа по серверному виду jsonb.

6. Страж 0000_guards (allowlist по oid, комментарий), права: execute только authenticated, anon нет; прямой INSERT/UPDATE/DELETE на duel_answers клиентом закрыт (проверь живьём через PostgREST под authenticated и anon); service_role права; триггеры duel_answers_before_insert / after_insert при вызове из RPC (двойная проверка: нет ли расхождений, когда RPC принимает, а триггер отвергает, или наоборот).

7. Гонки: перепроверь tools/duel_join_race.sh в обоих режимах (все 4 сценария с защитами OK; `--without-lock` показывает LOST/deadlock; функции восстанавливаются), deadlock между advisory и строкой дуэли и между двумя участниками, много дуэлей параллельно.

8. Мутации тестов: исполнитель заявил 18 SQL (все роняют 0009; две на политике роняют и 0007) и 20 клиентских, все убиты. Выборочно перепроверь 5–6 и придумай 5 НОВЫХ, которые тесты могут пропускать (например: `duplicate` после проверки срока; идемпотентность по любому пользователю вместо (дуэль, пользователь, вопрос); MS404 различается текстом для «нет дуэли» и «не участник»; p_user_id не сверяется, но auth.uid() подставляется; `FOR NO KEY UPDATE` → `FOR SHARE`; проверка вопроса из набора через `=` вместо `= any`; кап ответа по символам, а не байтам; `skipped` принимается без is_correct=false; победитель считается по `>=`; результат показывается по `localDone` вместо `finished`).

9. CI: job supabase-tests при `supabase db start` (только Postgres): RPC и триггеры не зависят от сервисов вне БД.

10. `python3 -I tools/check_invisible_chars.py` проходит; в новых файлах нет невидимых символов.
