## T09. Drift-схема и доменные модели
- **Цель:** локальное хранилище для контента, прогресса, логов и outbox.
- **Входы:** ТЗ §7.1, §7.3, T05 (рабочая настройка drift), T06 (модели колоды).
- **Сделать:**
  1. Удалить spike-таблицу.
  2. Таблицы:
     - `decks(id, version, title, topic, lang, downloaded_at)`;
     - `items(id, deck_id, title, fact, explanation_short, explanation_long, refs_json, retired)`;
     - `questions(id, item_id, type, prompt, payload_json, explanation_short?)`;
     - `user_item_state` (поля из §7.2 + `dirty`);
     - `review_logs` (поля из §7.2 + `synced_at`);
     - `outbox(id, kind, payload_json, created_at, attempts)`;
     - `hidden_questions(question_id)`.
  3. Индексы: `user_item_state(due)`, `questions(item_id)`.
  4. DAO с методами, нужными очереди и сессии, без бизнес-логики.
  5. Миграционная стратегия drift (`schemaVersion = 1`) и тест на создание БД in-memory.
- **Критерии приёмки:** тесты DAO (вставка колоды, выборка due-знаний, запись лога с обновлением состояния в одной транзакции) зелёные.
- **Проверка:** `flutter test test/core/db`.
- **Зависимости:** T05, T06. **Размер:** M.
- **Модель:** Sonnet — схема задана в ТЗ.

## T10. Каталог и загрузка колод
- **Цель:** колода с сервера попадает в локальную БД и обновляется по версии.
- **Входы:** ТЗ M2, §6.3, §7.1–7.2 (`decks`), T09.
- **Сделать:**
  1. Миграция `decks` + RLS (§7.2), bucket `decks` в Storage и политики.
  2. `tools/import_deck.dart`:
     - запускает `validate_deck --release`;
     - загружает файл в `decks/<id>/v<version>.json`;
     - делает upsert строки, ключ service role из `.env`;
     - отказывается импортировать, если `version` не больше текущей.
  3. Клиент: `CatalogRepository.list()` и `download(deckId)`. Парсинг JSON в изоляте (`compute`), запись в drift одной транзакцией. При обновлении знания, отсутствующие в новой версии, помечаются `retired = true`.
  4. Экран «Колоды»: список, состояния «скачать / скачано / обновить», ошибки сети.
- **Критерии приёмки:** AC2.1, AC2.2, AC2.3 (тесты на распаковку с фикстурами двух версий).
- **Проверка:** тесты + ручной импорт `sample.json` и скачивание на web и Android.
- **Из T09:** проверка коллизии `item_id` между колодами (ADR-21): `import_deck` и клиент отказывают с понятной ошибкой, если `id` знания уже есть в другой колоде. `DecksDao.replaceDeck` бросает `ItemIdCollisionError` как последний рубеж.
- **Зависимости:** T04, T09. **Размер:** M.
- **Модель:** Sonnet.

## T15. Edge Function `grade-open-answer`
- **Цель:** серверная оценка открытых ответов по контракту.
- **Входы:** ТЗ §4.2, §5.2, §5.5, M5, `supabase/functions/_shared/grading.ts` из T07, выбранная модель из T07.
- **Сделать:**
  1. Миграции `grading_cache`, `llm_usage` (RLS: только service role).
  2. Функция:
     - проверка JWT;
     - загрузка колоды из Storage с in-memory кэшем по `deck_id@version`;
     - поиск вопроса;
     - шаги 1–7 из §4.2;
     - вызов OpenRouter с `response_format` json_schema, таймаут 12 с, один повтор при невалидном JSON;
     - запись в `llm_usage`;
     - лимиты: пользовательский (30 в день) и глобальный бюджет из env.

  4. Deno-тесты с замоканным fetch: кэш, лимит → 429, невалидный JSON → `unsure`, required miss → не выше partial, contradiction → incorrect.
- **Критерии приёмки:** AC5.1 (локальный замер), AC5.3; все Deno-тесты зелёные; ключ нигде не логируется.
- **Проверка:** `deno test supabase/functions/grade-open-answer`; ручной `curl` на локальном стеке.
- **Зависимости:** T04, T07. **Размер:** M.
- **Модель:** Opus — безопасность, деньги и контракт.

## T25. Колода ИБ на 60–100 знаний
- **Цель:** контент для реального использования.
- **Входы:** `content/PIPELINE.md`, T08 (замеры времени).
- **Сделать:** прогнать конвейер по 5–7 подтемам ИБ, например:
  - веб-уязвимости (OWASP Top 10);
  - криптография (симметричная и асимметричная, хеши);
  - сети (порты, протоколы, TLS);
  - аутентификация (MFA, хранение паролей);
