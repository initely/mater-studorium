# Конвейер контента: инструкция куратора

Схема (ТЗ §5.4):

```
источники → [1] генерация (сессия A) → [2] validate_deck → [3] check_links
  → [4] верификация (сессия B, новая) → [5] вычитка человеком (approved)
  → [6] validate_deck --release → [7] import_deck → Supabase
```

Все команды — из корня репозитория. `dart` должен быть из Flutter SDK (системный бывает старше: `~/snap/flutter/common/flutter/bin/dart` или `flutter pub run …` вместо `dart run …`).

## 0. Подготовка
- Выбрать подтему и 2–5 открытых источников (ТЗ §5.3 п. 6): OWASP (CC BY-SA 4.0), RFC (IETF Trust), Википедия (CC BY-SA), открытая документация вендоров. Лицензию смотреть на самой странице или в репозитории проекта и записывать в `sources[].license`.
- Предпочитать стабильные URL: версионные страницы вместо `latest`, конечный адрес после редиректов (например, `https://community.owasp.org/attacks/xss/`, а не `owasp.org/www-community/...`). Страница, которая отдаёт 200 с «Redirecting…» в теле (JS/meta-редирект), цитату не пройдёт — брать её конечный адрес.

## 1. Генерация (сессия A)
Новая сессия Claude Code, промпт `content/prompts/generate.md` с подставленными подтемой, источниками и числом знаний (10–15 на порцию). Модель сама открывает страницы, пишет знания в `content/decks/<deck>.json` со статусом `draft` и прогоняет шаги 2–3.

## 2. Валидация схемы и семантики
```
dart run tools/validate_deck.dart content/decks/<deck>.json
```
Код 0 — OK; 1 — ошибки (путь JSON Pointer до проблемы); 2 — файл/схема не читаются. Этот же шаг выполняет CI для всех `content/decks/*.json`.

## 3. Ссылки и цитаты (сеть, вручную)
```
dart run tools/check_links.dart content/decks/<deck>.json
```
- Каждый URL из `sources` запрашивается GET один раз (редиректы до 5, таймаут 30 с, пауза 1 с между запросами, свой User-Agent); нужен итоговый 200.
- Каждая `refs[].quote` ищется в видимом тексте страницы после нормализации: без тегов, скриптов, стилей и комментариев; сущности раскрыты; регистр, пробелы, типографские кавычки/тире и `ё` не важны.
- `quote_unverifiable: true` — только проверка 200.
- Код 0 — проблем нет; 1 — есть проблемы (`[url]`, `[quote]`, `[ref]` с путём до ссылки и началом цитаты); 2 — неверные аргументы или колода не читается.
- Опции: `--timeout=<сек>`, `--delay-ms=<мс>`, `--user-agent=<строка>`.
- **В CI не запускается** (сеть, чужие сайты, нестабильность). Запускать вручную после генерации, перед вычиткой и перед каждым `import_deck`: страницы источников меняются, цитата может пропасть.

## 4. Верификация (сессия B, новая)
Новая сессия без истории генерации, промпт `content/prompts/verify.md`, на вход — файл колоды. Ответ сохранить в `content/reports/<deck>.verify.json` (папка в `.gitignore`). Знаниям с `verdict = needs_fix` поставить `review.status = "needs_fix"` и кратко записать замечания в `review.notes`.

## 5. Вычитка человеком
Для каждого знания: прочитать факт, цитаты (открыть страницу по ссылке), все вопросы и разборы; проверить, что в `mcq` ровно один верный ответ, в `cloze` учтены естественные варианты, в `order` порядок однозначен, в `find_error` нет ошибок в «правильных» строках. Исправить или удалить знание. Только после этого:
```json
"review": {"status": "approved", "by": "<имя>", "notes": ""}
```
Ставит `approved` только человек; модель этого не делает (ТЗ §5.3 п. 2). Знания с `needs_fix` после шага 4 вычитывать особенно внимательно. Выборочно 5 знаний вычитывает второй человек (критерий T08).

## 6. Релизная валидация
```
dart run tools/validate_deck.dart content/decks/<deck>.json --release
```
Падает, если хоть одно знание не `approved` (AC12.1). Перед этим ещё раз шаг 3.

## 7. Импорт
```
dart run tools/import_deck.dart content/decks/<deck>.json [--env=.env] [--allow-draft]
```
Что делает (AC12.3), по порядку; при любом отказе в Supabase ничего не записано:
1. Читает env-файл (по умолчанию `.env` в корне репозитория, в системе контроля версий его нет): `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`. Ключ service role живёт только там и в клиент не попадает. Для настоящего проекта нужен `https`.
2. Запускает `validate_deck --release` (все знания `approved`).
3. Отказывает, если `version` не больше текущей на сервере (увеличь `version` в колоде) или если `id` знания уже есть в другой колоде (ADR-21; для этого читает файлы остальных колод из Storage).
4. Загружает файл в bucket `decks`, объект `<id>/v<version>.json` (старые версии остаются), затем делает upsert строки `decks` (`visibility = public`, `item_count`). Файл идёт раньше строки: клиент не увидит колоду без файла.

Коды выхода: 0 — готово; 1 — колода отклонена (валидация, версия, коллизия); 2 — неверные аргументы или env-файл; 3 — сбой сети или сервера.

Пример `.env` для локального стека (`supabase status -o env`, поле `SERVICE_ROLE_KEY`):
```
SUPABASE_URL=http://127.0.0.1:54321
SUPABASE_SERVICE_ROLE_KEY=<SERVICE_ROLE_KEY>
```

### Локальный импорт черновика (`--allow-draft`)
Колоды со статусом `draft` (например, `sample.json`) `--release` не проходят. Для ручной проверки приложения на локальном Supabase:
```
supabase start
dart run tools/import_deck.dart content/decks/sample.json --allow-draft
```
`--allow-draft` пропускает только проверку `approved` (схема и семантика проверяются). Флаг **запрещён для не-локальных проектов**: `SUPABASE_URL` должен указывать на `localhost`, `127.0.0.1` или `::1`, иначе импорт отклоняется (код 2) до чтения колоды и до обращения к сети. Повторный импорт той же `version` отклоняется: увеличь `version` в файле или сделай `supabase db reset`.
