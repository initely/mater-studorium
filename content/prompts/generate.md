# Промпт генерации знаний (шаг 1 конвейера, ТЗ §5.4)

Запускать в Claude Code из корня репозитория (сессия A). Одна порция — одна подтема, 10–15 знаний. Перед запуском куратор подставляет значения в `<…>`.

---

Ты готовишь знания для колоды `<deck-id>` (файл `content/decks/<deck-id>.json`, язык `<lang>`, тема `<topic>`).

**Подтема:** <подтема>
**Сколько знаний:** <N, 10–15>
**Источники** (только они; ничего не добавляй от себя):
- `<source-id>` — <название> — <URL> — лицензия <лицензия>
- …

**Прочитай сначала:** `content/schema/deck.schema.json`, `docs/TZ.md` §4.1–4.4 и §7.1, `content/decks/sample.json` (образец качества и стиля).

**Порядок работы:**
1. Открой каждую страницу из списка (WebFetch или `curl`) и прочитай её целиком. Страница не открылась — не используй её и напиши об этом в ответе.
2. Проверь лицензию на самой странице (футер, страница лицензии проекта). В публичную колоду идут только открытые источники (OWASP — CC BY-SA 4.0, RFC — IETF Trust, Википедия — CC BY-SA, документация вендоров с открытой лицензией). Лицензия не подходит или не найдена — источник не используй.
3. Выбери <N> знаний: каждое — один проверяемый факт, который прямо следует из текста источников. Не дублируй знания, которые уже есть в колоде.
4. Для каждого знания напиши JSON по схеме и правилам ниже.
5. Добавь знания в `items` колоды, новые источники — в `sources`. Существующие `id` не меняй.
6. Запусти `dart run tools/validate_deck.dart content/decks/<deck-id>.json` и `dart run tools/check_links.dart content/decks/<deck-id>.json` и исправь всё, что они нашли.

**Правила знания:**
- `id`: `<topic>.<подтема>.<коротко>`, латиница в нижнем регистре, стабильный. `id` вопроса — `<id знания>.q1`, `.q2`, ….
- `fact` — одна-две фразы, сам факт без воды.
- `explanation_short` — 2–3 предложения: почему так.
- `explanation_long` — markdown до ~300 слов: механизм, пример, частые ошибки. Только то, что подтверждают источники.
- `refs` — 1–3 ссылки `{source_id, quote, quote_unverifiable: false}`. `quote` — **дословный** фрагмент текста страницы (одно-два предложения), скопированный, а не пересказанный. Не склеивай куски из разных мест в одну цитату. Цитата должна подтверждать ответ на каждый вопрос знания. `quote_unverifiable: true` — только если страница отдаёт 200, но текст недоступен скрипту (paywall), и с объяснением в `review.notes`.
- `review`: `{"status": "draft", "notes": "<что проверить при вычитке>"}`. Ставить `approved` модели **запрещено**: это делает только человек на шаге 5.
- `tags`: 2–4 тега.

**Вопросы (1–4 на знание, обычно 3–4, разных типов).** Тип выбирай по смыслу знания, а не для разнообразия:
- `flip` — определения и термины; `back` короткий.
- `mcq` — различение близких понятий. 3–5 опций, `multiple: false`, ровно один верный ответ. Неверные опции правдоподобны, но однозначно неверны по источнику; без «все перечисленные» и без подсказок по длине.
- `open` — объяснить механизм или «почему». `reference_answer` 1–3 предложения, `rubric` 2–5 пунктов с `weight` 1–3, хотя бы один `required: true`.
- `cloze` — ключевой термин или число. В `accepted` все естественные варианты (рус./англ., с дефисом и без); первый — канонический.
- `order` — только если порядок шагов однозначен (3–10 шагов).
- `find_error` — короткий фрагмент (до ~10 строк) с 1–2 ошибочными строками, в остальных строках ошибок нет; `line_explanations` для каждой ошибочной строки.
- Учебные примеры уязвимостей показывай на уровне, нужном для понимания защиты (как в источнике); не добавляй рабочих эксплойтов и полезных нагрузок сверх источника.

**В ответе после записи файла** перечисли: сколько знаний добавлено, какие источники не открылись или не подошли по лицензии, и 3–5 знаний, в которых ты меньше всего уверен, с причиной.
