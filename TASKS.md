## Как мы работаем

Оркестрация субагентами по карточкам задач (одна задача = одна ветка = один исполнитель):

1. Исполнитель (Sonnet; Opus для тонкой логики, указано в карточке) делает задачу в изолированном worktree/ветке, коммитит, не пушит.
2. Оркестратор проверяет сам: `dart format` (Dart из Flutter SDK), `flutter analyze`, `flutter test`, `supabase test db`, `supabase db lint --fail-on error`, гонки `tools/*_race.sh` в обоих режимах, `python3 -I tools/check_invisible_chars.py`, `bash tools/cloud/check_versions.sh`.
3. После любых RLS / RPC / Edge Function / Storage / Auth-задач запускается **Opus-ревью безопасности** (промпты-образцы: [docs/reviews/](docs/reviews/)), исправления отдаются тому же исполнителю, потом слияние в `main`.
4. Ничего не пушится наружу и не деплоится в облако без прямого подтверждения пользователя.

Один исполнитель за раз (лимит сессии, один локальный стек Supabase на одних портах). Всегда `supabase stop` по окончании работы, вывод `supabase start` не скрывать.

## Известные ограничения и решения, о которых нужно помнить

- **Дуэль**: доверие к клиенту (верность ответов и время присылает клиент), набор из 5 вопросов выбирает клиент создателя; приемлемо для беты без рейтинга (ADR-35). Дуэль **не влияет на FSRS** (ADR-16).
- **Скрытие вопросов по жалобам**: автоскрытие с защитами (аккаунт ≥ 24 ч, ответ на вопрос, потолок 20), решение «только после подтверждения куратором» оставлено владельцу (ADR-33).
- **Оценка открытых ответов**: модель и пороги предварительные (ADR-9, ADR-28), кредитный лимит ключа OpenRouter обязателен до облачного деплоя (ADR-31).
- Облачные Supabase/Firebase/Google проекты ещё не созданы; ни один GitHub workflow не запускался по-настоящему.
